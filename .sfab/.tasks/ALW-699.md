# ALW-699 Starter: domain activity events + entity UI (V2, after ops logging)

## Context

[[ALW-673]] split ops logging from ERP-style visibility. V1 ([[ALW-xxx]] light helper) only emits structured Workers Logs lines. Customers (ERP-shaped apps) eventually want **user actions / state changes** tied to a record, shown in the product (e.g. an activity tab on an item) — not every ops `console`/`structuredLog` line.

## Scope (draft — sharpen when picked up)

- Design a domain **activity / audit** API distinct from `@workspace/log` (e.g. `recordActivity({ entityType, entityId, action, actorId, payload })`).
- Persist in D1 (or agreed store); list by entity for UI.
- Prototype one surface (tab or panel on an existing starter entity) that reads activity, not Workers Logs.
- Optionally mirror a subset of activity events to `structuredLog` for ops — UI must not read the log stream.

## Acceptance criteria

- [ ] AC-1: Written model (kinds of activity vs ops log kinds; storage sketch). verify: task body or `docs/notes/`
- [ ] AC-2: Persisted activity for at least one entity type with a list API. verify: tests or local smoke
- [ ] AC-3: Minimal UI that shows activity for that entity. verify: browser walkthrough

## Non-goals

- Replacing or expanding `@workspace/log` / `noConsole`.
- Shipping a full ERP audit product in one PR.

## Boundaries

- ✅ Always: keep ops logs and activity events as separate APIs/sinks.
- ⚠️ Ask first: schema migrations; which starter entities get a tab first.
- 🚫 Never: dump raw ops errors into the user-facing activity feed.
