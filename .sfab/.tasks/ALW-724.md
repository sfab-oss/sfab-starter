# ALW-724 Skip Deploy on template when CLOUDFLARE_API_TOKEN is unset

## Context

The Option Y `Deploy` workflow (ALW-172) is the template CD contract for fabricated customer projects. On the upstream `sfab-oss/sfab-starter` template itself there is no Cloudflare account / `CLOUDFLARE_API_TOKEN`, so every post-merge Deploy run has failed since the workflow shipped. That paints merges (and linked tasks) with `deploy-failed` attention even though the template is not meant to deploy.

## Scope

- Extend the Deploy job `if` so the job only runs when `secrets.CLOUDFLARE_API_TOKEN` is non-empty (keep existing CI/main/push gates).
- Document in `docs/architecture/deploy-contract.md` that the upstream template is expected to conclude `skipped` when secrets are not provisioned; fabricated repos deploy once the provisioner writes the token.
- Keep `name: Deploy` and the deploy step sequence unchanged.

## Acceptance criteria

- [ ] AC-1: Deploy job is skipped (not failed) when `CLOUDFLARE_API_TOKEN` is absent/empty — verify: job `if` includes a token-present check; after merge on the template, Deploy run conclusion is `skipped` when secret unset
- [ ] AC-2: Deploy still runs when the token secret is present (fabricated-project path) — verify: token check is AND'd with existing gates, not a separate early-exit that breaks provisioned repos
- [ ] AC-3: `deploy-contract.md` states upstream-template skip expectation — verify: doc mentions skipped conclusion when secrets are not provisioned

## Non-goals

- Adding a Cloudflare account or Actions secrets to the template repo
- Renaming or deleting the Deploy workflow
- Changing platform observation of `workflow_run` / deploy phases

## Boundaries

- ✅ Always: keep `name: Deploy` stable; preserve Option Y step order for provisioned clones
- ⚠️ Ask first: any change to how the platform maps `skipped` vs `failure`
- 🚫 Never: delete the workflow file; push secrets into the template repo
